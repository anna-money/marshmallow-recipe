# PyO3 0.30: план проверки производительности

Дата анализа: 18 октября 2026. Это план дальнейшей работы, не результаты измерений.

## Вывод

Переходить на **0.30.1**: согласно changelog опубликованного crate, выпуск 0.30.0 не попал в crates.io из-за CI; 0.30.1 опубликован 14 октября и дополнительно подтверждает PyPy 3.12. Сначала измерить эффект обновления без переписывания сериализатора. Большая часть заметных ускорений конвертаций из release notes не относится к нашему пути выполнения.

Источники: [официальный релиз](https://github.com/PyO3/pyo3/releases/tag/v0.30.0), [changelog опубликованного 0.30.1](https://docs.rs/crate/pyo3/0.30.1/source/CHANGELOG.md), [migration guide](https://pyo3.rs/v0.30.0/migration.html). Changelog проверен также непосредственно в скачанном Cargo исходнике `pyo3-0.30.1/CHANGELOG.md`.

## Что получаем автоматически

| Изменение PyO3 | Применимость к нашему коду | Что измерять |
| --- | --- | --- |
| Упрощение и inline внутренних реализаций API, #6474 | Частые `cast`, проверки типов, `getattr`, вызовы и работа со словарями в `src/container_load.rs`, `src/container_dump.rs`, `src/fields/*`. Потенциальная польза без изменений; процент заранее неизвестен. | Транзакции, небольшие объекты, списки и словари. LTO уже включён, дополнительный эффект может оказаться мал. |
| Оптимизация reference pool, #6200 | Снижение внутренних расходов PyO3 возможно автоматически. Основная работа библиотеки происходит при подключённом интерпретаторе; не следует приписывать ей большой выигрыш от удаления `Py<T>` в отсоединённых потоках. | Общая задержка небольших load/dump; профилирование только если видны соответствующие расходы. |
| Быстрее `PyBytes::as_bytes`, #6377, уже в 0.29.3 | `src/fields/bytes.rs::dump_to_py` использует `extract::<&[u8]>`; в PyO3 это вызывает `PyBytes::as_bytes`. Cargo не включает `abi3`/`abi3t`, то есть fast path применим. Переписывание extract ради этого не требуется. | Bytes/base64 разных размеров, особенно маленькие значения. |
| Быстрее `i128`/`u128` на Python 3.15+, #6160, уже в 0.29.3 | `src/fields/int_type.rs::load_from_py`: строка → `i128` → Python int. Готовый Python int возвращается без этой конвертации; вне диапазона `i128` остаётся Python `int(str)`. | Числовые строки на 3.15 отдельно от готовых int и отдельно от 3.12–3.14. |

Эти пункты перечислены в [официальном changelog](https://pyo3.rs/main/changelog.html). Если исходная зависимость уже 0.29.3, два последних ускорения уже присутствовали: не считать их результатом именно 0.30.

## Что к нам не относится

- Оптимизация `num-bigint` на Python 3.14+ (#6144): feature/dependency `num-bigint` нет. Обычный Python int и наша ветка `i128` — другие реализации. Добавлять промежуточный BigInt только ради этой оптимизации оснований нет.
- Intern ключей в derive `IntoPyObject`/`IntoPyObjectRef` (#6446): таких derive у нас нет. Ключи динамических dataclass уже интернированы в `src/builder.rs::build_builder_field` и сохранены в `DataclassField`; dump использует `data_key_interned`. Переписывать динамические схемы в статические Rust structs ради derive нецелесообразно.
- Предварительное выделение Rust hash sets при extract (#6225, 0.29.3): коллекции обрабатываются как Python объекты через `Vec<Py<PyAny>>` и `PySet::new`, а не `extract::<HashSet<_>>()`. Такая замена меняет проверки, ошибки по индексам и поведение валидаторов.
- Исправление медленных вызовов `#[pyfunction]` (#6428): наш публичный путь — `#[pymethods] Container.load/dump`, `#[pyfunction]` в проекте нет. Не обещать соответствующий выигрыш.

## Небольшой полезный переход API

Кандидат отдельным изменением: заменить `py_string_char_count` в `src/fields/str_type.rs` на новый безопасный `PyStringMethods::code_point_len` (#6455). На обычном CPython >=3.12 PyO3 использует тот же `PyUnicode_GET_LENGTH`, который вызывается сейчас напрямую; это прежде всего устранение собственного unsafe и корректный выбор API для других интерпретаторов, а не ожидаемое ускорение.

Нужно распространить `PyResult<usize>` через текущую обработку `SerializationError`. Проверить ASCII, кириллицу, emoji, combining characters, lone surrogates, подкласс `str` с переопределённым `__len__`, strip и post_load. Семантика — количество Python code points, не байтов и не графем. Не заменять на общий `value.len()`, который может вызвать `__len__` подкласса. Сравнить строки с min/max length до и после; не принимать регрессию ради заявленной скорости.

## Последовательность работ и критерии

1. **Зафиксировать baseline.** В отдельных рабочих копиях собрать исходную зависимость и 0.30.1 одним Rust 1.99.1, одинаковым Python и release-профилем. Отдельное сравнение версий Rust проводить с одинаковым PyO3: иначе причины изменения скорости смешаются. Если старый PyO3 не проходит новый Clippy, это не запрещает release-сборку для baseline; production lints не ослаблять.
2. **Сравнить существующий набор.** `uv sync --extra dev`, `uv run maturin develop --release`, затем `uv run python benchmarks/bench_serialization.py --rigorous -o /tmp/pyo3-old.json` и аналогично `/tmp/pyo3-0301.json` в соответствующих окружениях. Сравнить `uv run python -m pyperf compare_to /tmp/pyo3-old.json /tmp/pyo3-0301.json --table`. Собирать строго последовательно; не запускать конкурирующие сборки и benchmark-процессы.
3. **Добавить прицельные benchmark cases отдельным изменением.** Маленькие bytes и 1 KiB/64 KiB; строки чисел `0`, границы `i64`, числа между `i64` и `i128`, границы `i128` и выход за них; те же числа как готовые int. Выполнить на CPython 3.12/3.14 и отдельно 3.15, если он входит в план поддержки. Добавить bytes- и integer-only dataclasses по образцу существующих datetime-only cases. Создание схем и данных вынести из измеряемого цикла.
4. **Подтвердить поведение.** Выполнить полный существующий pytest и CI matrix. Для чисел сохранить отрицательные значения, произвольную точность и исключение bool; для bytes — пустое значение, padding, ошибочный base64; для коллекций — ошибки с индексами и callbacks. `cargo fmt --check` и `cargo clippy` обязательны.
5. **Решать по измерениям.** Сохранить JSON pyperf и метаданные Rust/Python/ОС/архитектуры. Повторять статистически значимую регрессию на том же оборудовании. Ориентир для расследования — воспроизводимые >3% на целевых случаях; нестабильный или статистически незначимый результат не называть ускорением. Отчёт должен показывать абсолютное время и отношение, отдельно microbench и TransactionData.
6. **После baseline** сделать маленькую миграцию `code_point_len`. Дальнейшее изменение UUID/datetime, коллекций или владения `Py` рассматривать только после профиля: changelog 0.30 не обещает специального ускорения этих наших конвертаций.

Не включать `pyo3_disable_reference_pool` как часть обновления: это отдельный эксперимент с дополнительными требованиями к удалению Python объектов. Не менять unsafe пути выделения списков/base64 вместе с зависимостью — иначе трудно объяснить результаты и локализовать регрессии.
